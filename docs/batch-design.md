# GRSAI 批量图片任务节点设计

日期：2026-09-16。

状态：产品规则已讨论确认。2026-09-17 已按本文完成首版实现及离线/宿主验证，详见 [批量验证记录](batch-verification.md)；未执行新增付费测试。下文保留产品契约及验收要求，不代表所有环境或上游能力均已验证。

审查补充：已合并 UI 与 Prompt Variants 规则。Reference 先按 `{1, N}` 配出 N 个 Base Image Groups，再按 Base-major 顺序与 M 个 Prompt Variants 展开成 T=N×M 个任务。Folder Loader 双输出与节点 ID 已确认。`max_concurrency` 采用 INT 2–10，默认 4，约束最终 T 个任务；默认值是本地产品选择，不代表已验证的 Provider 吞吐能力。

本文补充 [单次生成设计](design.md)，不改变现有 `GRSAI Image` 的输入含义、节点 ID 或已保存工作流。批量能力使用独立节点，复用现有配置、请求构造及单次异步生成服务。

## 1. 目标与已确认决策

将多个有序图片序列按位置组成 Base Image Groups，再应用一组共享的 Prompt Variants，生成确定编号的一批任务。所有任务共用模型、模型参数和 API Key，通过受控并发提高处理效率。每项结果及时保存，文件编号稳定对应 Base 与 Prompt 的组合。

| 项目 | 决策 |
| --- | --- |
| 输入角色 | 不区分主图与参考图，统一使用 `reference_1`、`reference_2` 等图片插口 |
| 插口数量 | 动态增减，优先使用目标 ComfyUI V3 的 Autogrow；不写死为五个 |
| Reference 输入长度 | 每个已连接 Reference 序列只能有 1 张或 N 张；所有大于 1 的图片序列必须等长，不约束 Prompts 的 M |
| 单张输入 | 自动复用于全部 Base Groups，且同组图片复用于该组全部 Prompt Variants |
| 多张输入 | Reference 列之间按序号逐项配对，不做图片交叉组合 |
| Prompt 入口 | `Prompt` 为单一多行字符串；`Prompts` 为可连线的有序字符串数组 |
| Prompt 优先级 | `Prompts` 非空时覆盖 `Prompt`；未连接或空数组时使用 `Prompt`，不合并、不追加 |
| Variants | 固定 T=N×M，即使 N=M 也不自动 1:1 配对 |
| 任务顺序 | Base-major：先遍历 Base，再遍历 Prompt；提交前固定三个索引 |
| 执行边界 | T 个生成任务属于一次节点执行，禁止由默认 list mapping 多次执行节点 |
| 缓存与副作用 | 相同参数再次 Queue 是新批次、新 API 请求，不复用历史生成结果 |
| 共享参数 | 整批共用模型、模型参数和 API Key；每个 Base 使用同一有序 Prompt Variants 集合 |
| 文件夹排序 | 显式按文件名自然排序，不依赖文件系统遍历顺序或 Finder 显示顺序 |
| 图片处理 | 不缩放、不裁切、不补边；宽高不同不构成数量不匹配 |
| 调度 | 显式 INT 2–10，默认 4；限制最终生成任务而非 Base 数量，任务完成后补入下一项 |
| 保存 | 下载、校验成功的图片及时落盘，不等待整批结束 |
| 命名 | 用户提供前缀，例如 `Clothes`；按任务编号命名，不按完成顺序 |
| 对应关系 | 提交前固定任务编号、输入顺序和映射；失败不导致后续任务重新编号 |
| 记录 | 每批独立目录，保存 manifest，记录任务状态、输入对应关系、远端 ID 和输出 |
| 持久化边界 | 收到合法远端 ID 后立即写入任务状态并持久化 manifest，再继续轮询 |
| 状态写入 | 单一权威状态与串行 manifest 写入，不能让并发任务各自读改文件 |

首版不做 paired prompts、每任务独立模型参数、重复生成次数控件、通用 Cartesian-product UI、Reference 图片交叉组合、Prompt Mode 下拉框、Prompt 数量控件、按内容自动搭配、文件名编号匹配、短列表循环/截断/补图、图片预处理、自动重新生成失败项、SQLite/数据库、完整断点续跑、全局 API 队列、复杂限流器、复杂费用预测、自定义实时 Dashboard 或远端取消承诺。

本次确认的固定 `Base Groups × Prompt Variants` 取代旧稿“整批只能有一个 Prompt”的限制，但不引入任意维度的组合系统；原单次生成节点仍只处理一个 Prompt。

## 2. 任务模型

| 符号 | 含义 |
| --- | --- |
| K | 已连接 Reference 插口数，也是每个任务的参考图数量 |
| N | `{1, N}` 图片配对得到的 Base Image Group 数量 |
| M | 生效的 Prompt Variant 数量；使用单一 Prompt 时 M=1 |
| T | 最终生成任务数，T=N×M |

N 不再直接代表任务数，只有 M=1 时 T=N。每个任务仍只包含 K 张图片，而不是 K×N 或 K×M 张。

例如三个输入序列：

```text
reference_1 = [people]                         长度 1
reference_2 = [shirt_001, shirt_002, ..., 010]   长度 10
reference_3 = [pants_001, pants_002, ..., 010]   长度 10

Base 001 = [people, shirt_001, pants_001]
Base 002 = [people, shirt_002, pants_002]
...
Base 010 = [people, shirt_010, pants_010]
```

没有单独人物图时，直接连接多个等长参考序列即可。十张人物配十套衣服、十套衣服共用一张人物或一双鞋，都使用同一规则。

### 2.1 Reference 数量校验

1. 每个插口先按“ComfyUI 列表顺序 -> batch 内顺序”展开为单图序列。
2. 未连接的尾部备用插口不参与计算；已连接但得到空序列必须报错。
3. 至少需要一个已连接且非空的图片插口；纯文生图仍使用现有单次节点。
4. 取所有已连接序列的最大长度为 N。
5. 每列长度必须属于 `{1, N}`，否则在任何付费提交前报错。
6. 对 Base i，长度为 1 的列取唯一图片，长度为 N 的列取第 i 张。Reference 只负责 broadcast + positional zip。

| 输入长度 | 结果 |
| --- | --- |
| 1、10、10 | N=10，第一列共享 |
| 10、1、10 | N=10，每个 Base 复用第二列唯一图片 |
| 10、10 | N=10，每个 Base 两张图片 |
| 1、1、1 | N=1，不自动重复；最终任务数由 M 决定 |
| 10 | N=10，每个 Base 一张图片 |
| 10、9 | 报错，不补齐、不截断 |
| 10、5 | 报错，不循环复用五张图片 |

错误应指出具体插口与数量，例如：`reference_3 contains 9 images; expected 1 or 10.`

### 2.2 图片编号

每次 API 请求中的 `images` 按插口数字顺序组装：`reference_1` 对应提示词中的图片1，以此类推。不得使用字符串字典序把 `reference_10` 排在 `reference_2` 前面。

有效插口必须从 1 连续连接。中间断开而后面仍有连接时明确报错，不静默压缩编号；尾部未连接的 Autogrow 备用插口可以忽略。插口变动会改变图片编号，界面应反映当前顺序，但插件不自动改写提示词。

主图只是用户赋予某张图片的语义，不是插件的特殊类型；可放在任何插口，提示词需与实际顺序一致。

### 2.3 Prompt 与 Prompts

两个入口同时存在，优先级固定为 `Prompts > Prompt`：

| Prompts 状态 | 生效输入 | M |
| --- | --- | --- |
| 未连接 | Prompt 多行输入框或其上游单一字符串 | 1 |
| 已连接，但规范化后为空数组 `[]` | Prompt | 1 |
| 非空有序字符串数组 | 仅使用 Prompts，忽略 Prompt | 数组长度 |
| 非法类型或包含非字符串元素 | 提交前报错，不静默回退 | 不规划任务 |

`Prompt` 的换行属于同一提示词，不能按行或分隔符拆分任务。`Prompts` 接收上游 STRING list / Prompt array，保留上游顺序和重复项，不去重、不把 Prompt 追加进去，也不根据图片数量裁剪或补齐。两个入口都不会把字符串中的 JSON 文本自动解析成数组。

适配层需区分 ComfyUI 的外层列表包装与实际 Prompt array：以有序字符串序列为统一内部类型，对明确的上游数组只解包其约定的一层，不递归猜测任意嵌套结构。普通单一 STRING 连到 Prompts 时视为一个 Variant；不同上游节点的实际包装通过宿主测试确认，不宣称兼容所有 Prompt Array 插件。

“为空”指数组长度为零，不是数组中某个字符串为空。例如 `[""]` 仍有一个元素，不能因为内容为空就改用 Prompt。字符串内容原样保留并沿用现有单次请求的合法性校验，不自动删除空项或修剪内容而改变 M 与编号。所有生效的 Variant 均在首个 POST 前完成可预检校验；忽略的 Prompt 不参与请求、计数或提示词指纹。

### 2.4 Variants 与 Base-major 编号

每个 Base 都使用全部 M 个 Prompt Variants。10 个 Base 与 4 个 Prompts 固定生成 40 个任务；10 个 Base 与 10 个 Prompts 固定生成 100 个任务，绝不因 N=M 自动切换成 paired prompts。

```text
for each Base Image Group:
    for each Prompt Variant:
        create one generation task

Base 001 + Prompt 001 -> Task 001
Base 001 + Prompt 002 -> Task 002
Base 001 + Prompt 003 -> Task 003
Base 001 + Prompt 004 -> Task 004
Base 002 + Prompt 001 -> Task 005
Base 002 + Prompt 002 -> Task 006
...
Base 004 + Prompt 002 -> Task 014
```

`base_index`、`prompt_index`、`task_index` 均从 1 开始：

```text
task_index = (base_index - 1) * M + prompt_index
```

同一 Base 的不同提示词任务连续编号，不受并发完成顺序影响。原始图片顺序由 `base_index` 定位，实际请求提示词由 `prompt_index` 定位，保存和远端任务状态由 `task_index` 定位。任务只是引用对应 Base 和 Prompt，不为每个 Variant 复制整份输入 tensor。

### 2.5 一次执行与 List 输出

T 个最终生成任务属于一次 `GRSAI Batch Image` 执行。节点一次拿到完整 References、Prompt/Prompts、模型、尺寸、质量、Key、并发等输入，自行规范化并规划，不使用 ComfyUI 默认 list mapping 按图片或提示词多次调用节点。按目标 V3 API 设置全列表接收语义；动态输入字典中的各列也必须保持正确的列表包装。

模型、尺寸、质量、Key、并发和输出前缀等普通参数仍要求恰好一个值。只有 References 和 Prompts 按各自明确的序列规则处理；不能因为启用全列表接收，就让其他参数参与任意广播。回退生效时的 Prompt 同样必须是一个字符串。

输入处理顺序固定为：

```text
Reference socket order
  -> 每个插口的 ComfyUI IMAGE list order
  -> 每个 IMAGE batch 内部顺序
  -> 该插口的单图序列
  -> 跨插口执行 {1, N} 校验和逐项配对，得到 N 个 Base
  -> 解析 Prompt/Prompts 优先级，得到 M 个 Variants
  -> 按 Base-major 展开 T=N×M 个任务
```

不能先把所有插口合并成一条单图列表而丢失列边界。整批执行完成后，将成功下载、校验并保存的结果按 `task_index -> result_index` 平铺为一个 IMAGE list，每项保持单图张量 `[1,H,W,3]`：

```text
Task 1 -> img_1
Task 2 -> img_2a, img_2b
Task 3 -> failed
Task 4 -> img_4

IMAGE list = [img_1, img_2a, img_2b, img_4]
```

声明 list 输出，使后续 Upscale、Save、Edit 等节点按各自的列表契约消费。失败任务不插入占位图；任务部分下载失败时，已保存的有效图片同样保留，并在报告中标明任务未完全成功。完整 Task 与 Output 映射由 manifest/report 提供，不能从平铺列表下标反推原任务编号。

及时保存发生在节点内部；普通 IMAGE list 输出在本次执行结束后一次返回，不承诺流式驱动下游节点。

实施确认：目标宿主对空 IMAGE list 的下游默认 mapping 会报索引错误。因此没有任何成功图片时，图片输出使用宿主 ExecutionBlocker 跳过图片分支，manifest 输出仍正常返回；此值不是占位图。部分成功仍输出有效图片列表。

## 3. 节点界面

只新增两个节点，全部放在 `GRSAI` 分类，不按 Nano Banana / GPT Image 拆分：

| 显示名称 | 稳定节点 ID | 状态 |
| --- | --- | --- |
| GRSAI Image | `GRSAIImageGenerate` | 现有单次节点，不改名或改变语义 |
| GRSAI Load Images From Folder | `GRSAILoadImagesFromFolder` | 新增，名称与 ID 已确认 |
| GRSAI Batch Image | `GRSAIBatchImageGenerate` | 新增，名称与 ID 已确认 |

### 3.1 文件夹加载节点

显示名称：`GRSAI Load Images From Folder`。

- 输入：ComfyUI 后端可访问的文件夹路径。远程部署时不是浏览器所在电脑的路径。
- 首版只读取该目录，不递归子目录；隐藏文件、非图片文件忽略。
- 图片格式沿用明确的静态图片支持范围；损坏图片不能静默跳过。
- 双输出：自定义 `references` 与标准 `images`，包含同一有序图片序列，保留各自尺寸。
- 展示：图片数量、有序文件清单；必要时提供轻量预览。
- 保留来源文件名及顺序信息，供配对清单与 manifest 使用；不从张量猜测文件名。

| 输出 | 数据与用途 |
| --- | --- |
| `references` | 自定义图片集合，包含 IMAGE、排序后的 source filename、source path/source information、sequence index 和必要追溯 metadata；主要接 Batch 的 Reference 插口 |
| `images` | 标准 ComfyUI IMAGE list，每项 `[1,H,W,3]`，供 Preview、Save Image、Upscale 及其他普通 IMAGE 节点使用 |

两种输出尽量引用同一份 IMAGE tensor，metadata 只增加轻量记录，不复制完整图片数据。集合内图片与来源记录数量相同，按相同顺序一一对应；序列位置对用户从 1 编号，不能把文件名编号当作 sequence index。自定义类型的具体标识与 V3 适配形式属于实施细节，不再把是否双输出或是否传 metadata 当作产品待决项。

Folder Loader 使用路径输入框，不增加加载按钮；跟随工作流执行。建议只读文件清单默认折叠，加载完成后显示数量及有序文件名。

建议首版支持 PNG、JPG/JPEG、WEBP。透明、多帧等输入兼容范围沿用现有项目契约，不在批量功能中暗中新增 alpha 或动画处理能力。

文件夹缓存必须感知目录内容变化。不能只因路径字符串相同而永久复用旧结果；实施时确定是每次重新加载还是以有序文件清单和内容指纹失效。

首版允许读取 ComfyUI Server 所在机器上、服务进程有权限访问的本地目录，不额外引入 filesystem sandbox 或 allowed roots。此范围面向可信本地使用，不意味着已完成公网/多用户安全隔离；相关隔离留待部署需求明确后设计。

### 3.2 批量执行节点

显示名称：`GRSAI Batch Image`。

| 输入 | UI | 行为 |
| --- | --- | --- |
| `references` | Reference 1、Reference 2 等动态插口 | 每口同时兼容 GRSAI 自定义图片集合和普通 IMAGE list/batch；图片仍按 `{1, N}` 规则形成 Base |
| `api_key` | API Key | 与现有节点一致，整批共享 |
| `model` 与模型参数 | 模型下拉及对应参数控件 | 整批共享；Nano 比例/分辨率、GPT 尺寸/质量沿用现有控件 |
| `prompt` | Prompt 多行 STRING 输入框，可接上游单一 STRING | 默认提示词，Prompts 未连接或为空数组时生效 |
| `prompts` | Prompts 可选连线插口 | STRING list / Prompt array，非空时覆盖 Prompt；始终表示 Variants |
| `max_concurrency` | Max concurrency | 显式 INT，min=2、max=10、default=4；前后端均校验，限制最终生成任务，不是平台配额 |
| `output_prefix` | Output prefix | 例如 `Clothes`，用于保存文件名；建议默认 `GRSAI` |

固定输出 `images`（平铺的标准 IMAGE list）和 `manifest`（STRING 文件路径，指向包含完整状态与映射的报告）。图片输出遵循第 2.5 节，按任务编号、结果编号排序，不按完成顺序。

Reference 插口与 Prompts 连线输入放在节点上部，模型与 Prompt 控件居中，并发、保存及只读状态位于下部。Prompt 在被 Prompts 覆盖时仍保留原值，不清空、不合并。首版不添加 Prompt Mode、Prompt 数量控件、生成/重试按钮或保存开关，统一跟随 ComfyUI Queue 执行并自动保存。

不新增第三个 Prompt Array 节点。用户通过已有上游字符串列表节点提供 Prompts；不为此内置提示词分割器或复杂编辑器。

动态输入优先使用原生 Autogrow，不先写自定义前端整数控件来模拟插口。具体呈现是连接后自动增加空口，还是宿主支持的加减操作，以目标版本实测为准。用户目标是可增减的连续插口，不锁定尚未验证的 UI 实现。

Reference 必须连续连接，中间空洞由后端明确报错，不依赖 Autogrow 自动修复或重新编号。首版不承诺 Subgraph 等特殊场景完全兼容；不为兼容这些场景开发复杂自定义前端。

### 3.3 非幂等付费执行与版本边界

批量生成包含付费副作用、远端生成和非确定性结果。相同参数再次 Queue 必须创建新的批次目录和新的任务，不能因缓存命中复用历史生成，也不能将输入相同的两个付费节点合并为一次调用。

按目标 ComfyUI V3 API 设置终端输出节点与非幂等/缓存行为，使节点只用于内部保存、不连接下游时也能执行；同时支持连接下游的 IMAGE list 输出。参考现有节点的 `not_idempotent`、`fingerprint_inputs`，但必须在宿主中验证组合行为，不能只凭字段存在宣称正确。文件夹加载缓存与生成节点缓存是两个边界，不关闭其他节点的正常缓存。

实施和验证记录必须列出实际的 ComfyUI Core、ComfyUI Frontend 和 `comfy_api` 版本；如果 `comfy_api` 随 Core 发布且无独立版本，记录所用 API 命名空间及对应 Core 版本/提交，不编造版本号。

### 3.4 简单进度

优先使用 ComfyUI 原生 progress。至少展示 `Completed / Total`，分母固定为最终任务数 T=N×M，不是 N 或 M。Completed 表示已结束本地处理的生成任务数，包含成功和失败，不等于成功图片数；重连中和仍在运行的任务不计入。中断或全局错误停止提交时，未提交项保持未提交，不为达到 100% 而伪装完成。

```text
提交前：计划：10 组图片 × 4 个提示词 = 40 个任务 · 并发 4
运行中：已完成：17 / 40
结束后：完成：成功 38 · 失败 2
        保存目录：...
        剩余积分：...
```

宿主原生接口容易支持时可附加 `Running 5 | Success 12 | Failed 1` 一类简短状态；部分成功需在报告中明确，不用六七个独立实时计数器或自定义 Dashboard。最终完整状态以 manifest 为准，不把某个任务的远端百分比当成整批百分比。

整批正常结束后独立刷新一次余额，不逐任务刷新。用户中断后的余额处理沿用现有节点规则。

## 4. 文件排序与可追溯性

文件系统没有可依赖的“文件夹内排列顺序”。加载节点显式对文件名自然排序，使 `1.png`、`2.png`、`10.png` 按数字直觉排列。

建议用户采用统一、补零的搭配编号：

```text
上衣/001_白衬衫.png
上衣/002_黑外套.png
裤子/001_牛仔裤.png
裤子/002_西裤.png
```

补零且长度统一时，普通字典序也会把 `001`、`002`、`010` 排对；自然排序主要解决未补零数字的顺序。实现应为大小写或数值相同的排序键定义稳定的次级比较规则，不把文件系统顺序当作平局规则，也不依赖系统语言环境的中文排序。

**首版按排序后的位置配对，不提取文件名编号作为连接键。** `base_index` 表示排序后的图片组位置；`Clothes_001.png` 中的编号则是 Base-major 展开后的 `task_index`，不必然对应原文件名中的 `001`。M=1 时 task_index=base_index；M>1 时必须通过 manifest 的三个索引还原来源。如果两个目录分别缺了不同文件、数量却相同，长度校验无法发现语义错配；必须通过有序配对清单核对，不能宣称能识别衣服是否搭配正确。

每批在提交前固定输入清单、任务索引和来源映射。执行过程中不重扫目录并重排后续任务。已加载张量作为本批输入快照；若未来采用延迟读取文件，必须检测文件内容变化并报错，不能在同批中悄悄换图。

标准 IMAGE 不包含文件名传递契约。来源信息通过已确认的 `references` 自定义集合显式传递，不增加第二套 metadata 连线，也不使用隐式全局张量映射。连接 Folder Loader 的标准 `images` 输出或第三方 IMAGE 时仍可执行，但没有 metadata 的来源文件名记为 `unknown`，保留插口与列内位置；不能根据连接节点名称、tensor 地址或相似像素推测文件名。

集合归一化时必须保持图像与 metadata 同步展开；来源记录缺失、长度不匹配或结构非法不能造成错配，应在提交前报错。全批、Base 和各 Variant 引用同一有序来源记录，不能把一个 Base 的文件名错误归到后续 Base。

## 5. 执行流程与并发

```text
收集所有输入
  -> 展开普通 IMAGE 或自定义 references，按 {1, N} 形成 N 个 Base
  -> 按优先级规范化 Prompt/Prompts，得到 M 个 Variants
  -> 校验所有生效提示词、图片、metadata 与共享参数
  -> 按 Base-major 规划 T=N×M 个任务，固定三类索引与输入映射
  -> 校验前缀、创建独立批次目录并写初始 manifest
  -> 显示 Batch Plan：N 组 × M 个提示词 = T 个任务、K 张参考图、模型、最大并发
  -> 对最终 T 个任务执行有界并发
  -> 每任务最多提交一次，解析合法远端 ID
  -> ID 写入内存状态并立即持久化 manifest
  -> 按远端 ID 轮询（直接成功时进入结果处理）
  -> 每张结果下载、解码、保存并更新 manifest
  -> 当前任务结束，补入下一个任务
  -> 汇总有序输出与完整报告，刷新余额
```

- 所有可预检的输入错误在首个 POST 前失败，不边付费提交边发现后续组数量错误。
- 并发槽覆盖单次任务的提交、等待、下载和保存过程；不只限制瞬时 POST 数量。
- 每个任务独立拥有 task ID、远端状态、查询/重试状态、错误和输出状态；HTTP 会话是否共享是实现选择，不是任务隔离的产品契约。
- 使用现有异步客户端和有界 worker 调度，不照搬参考插件“一项一个线程且全部同时提交”。
- 未设总任务时限时，持续运行或重连的任务会占用并发槽；用户可沿用现有总超时配置或主动中断。
- 一次批量节点执行内限制并发，不宣称限制整个 ComfyUI 或同一 Key 在其他程序中的并发。
- 共享单张图片尽量只编码一次；其余按并发需求编码，不预先生成整批的多份 base64。
- 同一 Base 的全部 Variants 复用相同图片和编码；只替换实际请求的 prompt，不将 T 个任务各自深拷贝为一整套 tensor/base64。
- 下载会累计已保存的图片。若输出全部 IMAGE 张量，仍可能占用大量内存；不能把即时保存等同于内存自动释放。

继承单次客户端的提交一次、查询退避、下载有限重试和取消语义。不因某项失败而重新运行整批，不通过改变参数或编码方式自动重发 POST。

### 5.1 Batch Plan 与并发范围

首个 POST 前显示并写入初始 manifest：`Base groups: N`、`Prompt variants: M`、`Planned tasks: T`、`References per task: K`、`Prompt source: prompt/prompts`、`Model`、`Max concurrency`。UI 明示乘法结果，例如 `10 组图片 × 10 个提示词 = 100 个任务`，不能在 N=M 时只显示十项计划或用隐藏配对规则降低任务数。计划显示不要求二次确认系统，也不做费用估算。首版不增加 `max_tasks`；以后若实际使用出现误提交大批任务，再考虑本地任务数保护。

`max_concurrency` 表示当前 Batch 最多同时持有多少个最终生成任务的生命周期槽，旨在控制进行中的远端任务数量。槽覆盖 `submit -> generation/polling -> download -> save`，任务结束即补位；当 T 小于设置值时实际最多运行 T 项。默认 4，用户可主动调至 8–10；后续只根据真实测试调整默认值，不预设 Provider 能承受十项。

例如 N=10、M=4、T=40、并发=4 时，同时最多运行四个生成任务，不是四个 Base 各启动四个 Variants 后实际并发十六项。不在 Base worker 内再嵌套一个独立并发器。

该参数不是 HTTP 每秒请求数限制，也不是全局 Key 配额。取消本地等待或提交响应丢失时，远端任务可能仍在运行；因此不能保证服务端实际存活任务数严格等于本地占槽数，更不能承诺跨批次或跨程序的远端硬上限。

### 5.2 远端 ID 的即时持久化

POST 返回合法 `task_id` 后，按以下顺序完成一个可等待的持久化步骤：

```text
解析 task_id
  -> 更新权威内存 TaskState
  -> 单写者立即原子写入 manifest
  -> 写入成功后才进入 polling 或直接成功的结果处理
```

该路径不得依赖最终图片回调、UI 进度事件或整批结束回调。返回直接成功、明确失败但附有合法 ID 的响应，也应尽早记录已知 ID。正常取消清理应尽力等待正在进行的这一步持久化结束，不能留下无主后台写入。

ID 持久化失败按存储级致命错误处理，停止后续提交并保留能安全报告的 ID；不能假装远端未创建任务，也不能重新 POST。没有收到 ID 时只能记录提交状态未知，无法凭空恢复 ID。该措施减少已知 ID 丢失风险，但不承诺覆盖进程瞬间终止、断电或磁盘故障，不引入数据库或完整 crash recovery。

### 5.3 状态与 HTTP 会话生命周期

优先在可保持清晰边界的情况下复用批次级 HTTP session/connection pool，每个请求使用正确的凭据，每项 TaskState 独立。API 请求和 CDN 下载的认证边界仍须隔离，禁止把默认 API 认证头带到 CDN。

当前客户端在单次生成内创建会话，若首版拆分代价过高，可以暂时保留每任务独立客户端/会话；这只是实现取舍，不把“一项一个 HTTP client”写成长期契约。共享会话应由 Batch 统一创建与关闭，在所有 worker 和写入清理完成后释放，不由某个 worker 提前关闭。

### 5.4 临时压力与 Rate Limit

区分任务局部错误、整批致命错误及 Provider 临时压力。生成失败或审核拒绝通常只影响当前任务；明确的无效 Key、账号禁用、全局配置错误和存储不可用应停止后续提交。HTTP 429、过载或明确的临时额度压力不直接等同于账号禁用，也不能仅凭模糊错误字符串猜测恢复条件。

首版不做 token bucket 等复杂 rate limiter。收到可靠的 `Retry-After` 或等价恢复信息时，可以由协调器维护一个简单、可取消的批次提交冷却时间：未发出的任务等待冷却结束，多个信号不能缩短已有冷却；轮询和下载继续遵循各自的退避规则。冷却是暂停其他未提交任务，不是重试已经发送的生成请求。

无论是 429、超时还是响应丢失，已发出的生成 POST 均不自动重提；尤其不能对创建结果未知的请求重复生成。Provider 没有给出可靠恢复信息时，不编造配额重置时间或吞吐保证。

## 6. 保存、编号与覆盖保护

用户输入 `output_prefix = Clothes` 时，正常单结果任务命名为：

```text
<ComfyUI output>/grsai/<批次时间_唯一标识>/
  Clothes_001.png
  Clothes_002.png
  Clothes_003.png
  manifest.json
```

前缀保留用户大小写；`Clothes` 不自动改成 `clothes`。前缀只作为文件名片段，不允许路径穿越或目录分隔符；空值、非法字符的校验规则在实施时明确展示。输出基目录复用 ComfyUI 的输出路径，不假设固定安装位置。

任务编号从 1 开始，至少三位；超过 999 时自然扩展，不截断。编号在提交前按 Base-major 固定，使用 `task_index`，不把 Base/Prompt 信息全部塞进文件名。例如 N=10、M=4 时保存 `Clothes_001.png` 到 `Clothes_040.png`；任务 014 对应 Base 004 + Prompt 002，而不是输入目录第十四张图。

例如任务 003 最先完成，它仍保存为 `Clothes_003.png`；任务 002 失败时，保留编号空缺，不把任务 003 改名为 002。成功图片列表可以缺少失败项，因此下游不能只靠列表位置推断原任务编号，必须使用报告映射。

一个远端任务返回多张图片时使用：

```text
Clothes_014_01.png
Clothes_014_02.png
Clothes_015.png
```

收到成功响应中的完整结果列表后即可确定单张或多张命名方式，无需等待所有图片下载。每张图片通过解码校验后立即保存，不等同任务的其他图片或整批结束；后续图片失败不能删除之前已保存的图片。

保存使用同目录临时文件并在写入完成后原子替换为最终文件；manifest 更新也采用原子替换。批次目录以排他方式创建并避免重名，不覆盖历史批次。磁盘故障时不能保证还能写入错误记录，应明确报告最后成功持久化的位置。

这属于运行中及时保存，不等于已承诺断电级持久化。若需要更强保证，另行设计文件同步与崩溃恢复。

批量执行器保存的 PNG 不写入 API Key 或含 Key 的完整工作流元数据。执行器自动保存是基础行为；再连接 Save Image 可能产生额外副本，不替代内部及时保存，且其工作流元数据存在第 7.2 节说明的宿主安全边界。

## 7. Manifest 与失败语义

manifest 至少记录：

- 格式版本、批次 ID、开始/结束时间、共享模型参数、K/N/M/T、实际 Prompt 来源、并发设置和输出前缀。
- 有序 Base 映射：base_index、各插口的列内 sequence index、是否复用、已知来源文件名/来源信息和必要的输入指纹。
- 有序 Prompt Variants：prompt_index 与 prompt fingerprint；即使提示词相同也保留各自索引，不去重。
- 每个生成任务的 task_index、base_index、prompt_index，以及可直接读取或通过这些索引解析的 reference mapping 和提示词指纹。
- 已知远端 task ID、远端状态、本地执行阶段、已保存结果及清理后的错误。
- 输出在成功图片列表中的位置，以及对应的任务编号和任务内结果编号。
- 批次结束状态：全部成功、部分成功、失败或中断；成功任务数与保存图片数分别统计。

不记录 API Key、认证头、base64 或默认持久化 CDN URL。首版继续优先只记录生效 Prompt 的指纹，不要求明文持久化，但必须保留 prompt_index、原始顺序和优先级选择结果。Prompt 被覆盖时不把其内容写入报告；指纹用于比对，不承诺能还原提示词或完全隐藏低熵内容。

下例省略其他字段，仅说明 M=4 时的索引与输出映射（任务内 result_index 从 1 开始，flat_output_index 明确采用从 0 开始的 IMAGE list 下标）：

```json
{
  "task_index": 14,
  "base_index": 4,
  "prompt_index": 2,
  "outputs": [
    {
      "result_index": 1,
      "file": "Clothes_014_01.png",
      "flat_output_index": 12
    },
    {
      "result_index": 2,
      "file": "Clothes_014_02.png",
      "flat_output_index": 13
    }
  ]
}
```

示例中的平铺位置假设之前任务共保存了十二张图，不能通过 task_index 直接计算。结果即时保存时尚不知道完整平铺位置，可先记为未确定，整批汇总后由单写者按任务/结果顺序补齐；中断报告仍保留已有文件与三个索引，不伪装已经输出下游列表。

### 7.1 单一权威写者

manifest 的权威状态只有一份，由 Batch Coordinator 拥有。worker 发送带任务编号的状态事件，协调器更新内存状态并串行原子写入。首版也可以使用一个 `asyncio.Lock`，但临界区必须覆盖共享状态变更、快照生成和写入完成，不只是锁住最后一次文件替换。

禁止各 worker 各自执行“读取 manifest -> 修改自己的副本 -> atomic replace”。原子替换只能避免半写文件，不能解决过期快照覆盖其他任务更新。单写者模型同样覆盖远端 ID、已保存文件、中断和最终报告，不能在旧快照写入尚未结束时启动可能倒序落盘的新写入。

关键事件立即持久化；高频进度可以只更新 UI，不要求每次轮询都写 manifest。最终汇总必须等待所有在途状态写入完成；正常退出不能遗留后台 writer。全批只维护内存状态与一个 JSON 文件，不增加数据库或持久化消息队列。

### 7.2 API Key 与工作流安全边界

API Key 不进入批量功能产生的 manifest、日志、文件名、PNG 元数据、CDN URL 或错误文本。报告、UI 事件与新增节点属性不得复制 Key；包括上游返回文本在内的错误在展示或持久化前脱敏。

**当前单次节点没有安全 Key 存储：`api_key` 是普通工作流输入，可能存在于 workflow JSON、API workflow、历史及下游 Save Image 的嵌入工作流元数据中。** Batch 沿用此已披露方式，不声称这些载体完全不含 Key，也不在本次文档修改中扩展为新的密钥管理项目。

验证目标是批量功能不新增凭据副本和泄露路径：检查 workflow JSON、API workflow、嵌入工作流元数据与插件新增属性，确认 Key 只处于原有、已披露的凭据输入边界；内部生成的 PNG 必须不携带 Key。下游 Save Image 的已知风险继续明确提示，不能承诺控制第三方保存节点。未来若项目提供安全 Key 管理，批量节点直接复用。

### 7.3 失败与恢复边界

本地阶段与远端状态必须分开。例如本地已中断并不能把远端 `running` 改成 `failed`。

| 情况 | 批量行为 |
| --- | --- |
| 本地输入、长度或参数无效 | 全批提交前失败，不发生成请求 |
| 单个远端任务明确失败或违规 | 记录原任务错误，其余独立任务继续 |
| 提交响应丢失且无任务 ID | 标记提交状态未知，不自动重新生成 |
| 查询暂时失败 | 查询同一个 ID，继承现有退避规则 |
| 429、过载或明确临时压力 | 按第 5.4 节区分阶段；可靠恢复信息可延迟未提交项，已发出的 POST 不重提 |
| 生成完成但部分下载失败 | 保留已保存图片，明确部分结果未取回；不重新生成 |
| 无效 Key、账号禁用或全局配置错误 | 停止提交后续任务，明确记录已提交任务的本地处置情况 |
| 输出目录或磁盘不可写 | 停止后续提交并报告保存错误，不伪装成功 |
| 用户中断 | 停止新提交，取消并等待本地子任务清理，保留已保存文件与已知 ID |

不能返回黑图、原图或其他占位图充当成功结果。报告区分待提交、已提交、状态未知、远端失败、下载未完成和已保存等情况。

恢复查询/下载与重新生成是不同操作。前者优先利用已有 ID，后者创建新任务并可能再次计费。第一版必须保留恢复所需的已有 ID 和文件记录，但独立恢复节点、自动断点续跑不属于本次已确认实施范围。重跑整个批量节点默认是新批次，会重新提交，不能误称为恢复。

结果查询可用期限和 CDN URL 有效期尚无可靠保证，不能承诺旧任务永久可恢复。

## 8. 实现边界与待验证项

现有 `client.py` 的 `generate()` 在全部结果下载成功后才返回图片，因此直接循环调用它只能实现每任务保存，不能满足多结果任务的逐张及时保存。实施时需要在单次服务内部提供可等待的结果回调或等价接口，让批量执行器逐张保存；保留原单次节点的全部成功才输出语义。

另外需要提供“已解析合法远端 ID”的可等待通知，以满足第 5.2 节的持久化顺序。该通知与图片结果通知都属于业务生命周期接口，不能复用可忽略失败的 UI 通知来实现。此处只明确所需行为，不要求顺带重构整套客户端。

建议职责分离：文件夹加载与排序、输入规范化/任务规划、有界异步调度、结果保存/manifest，以及 ComfyUI 节点与 UI 适配。具体文件划分根据实施时代码结构决定，不为设计文档预先加入空抽象。

以下属于实施前或实施中的必要验证，不是已验证能力：

1. 记录 Core、Frontend、`comfy_api` 的实际版本，验证 Autogrow、自定义 references/普通 IMAGE 的联合输入、全列表语义、连续插口及保存重载；Subgraph 等特殊场景不作首版保证。
2. 验证已确认的 Folder 双输出：图片与 metadata 对齐、数据不重复复制、标准 IMAGE 独立可用；具体自定义类型结构与 V3 适配留给实施，不再另选 metadata 连线方案。
3. 正确设置终端输出与非幂等/缓存行为：只为保存也能执行，相同输入再次 Queue 为新批次，同输入节点不合并。
4. 部分成功和全失败时的节点返回契约、报告可获取方式，以及下游 Preview/Save 行为。
5. 输出全部 IMAGE 的内存成本；是否需要后续提供仅保存模式，首版不默默丢弃图片输出。
6. 前缀校验、自然排序的确定性规则和目录变化的缓存失效。
7. 按第 8.1 节实现模型官方上限和明确标记的本地保护上限，不把 Autogrow 视为 API 无上限。
8. 验证 STRING list / Prompt array 的宿主包装与空数组回退；只剥离约定包装，不拆分字符串、不猜测 JSON、不自动配对 N=M。

当前 GRSAI 新接口快照将 `images` 声明为支持 base64/URL 的数组，未明确数量上限、总请求大小限制或并发配额。插件不得把五个插口、参考项目的十个插口或其他厂商直连接口的限制当成 GRSAI 保证。后续需官方依据或明确授权的边界测试；本地资源保护上限必须标为本地设置。

### 8.1 Reference 数量保护

优先支持模型配置中的 `model.max_reference_images` 或等价字段。存在可靠、适用于当前 GRSAI 模型/渠道的官方上限时，按实际每任务图片数 K 在 POST 前校验，并保留能力来源。不能只因同名底层模型在其他 Provider 有上限，就直接套用。

没有可靠官方限制时允许设置明确标记为 `local safety limit` 的本地保护上限。若首版需要统一保护值，可在 8–10 张范围内选择，具体值待实施确定；它属于可配置的资源保护，不把动态界面重新写死为五个插口，也不能宣称是模型能力。

官方限制与本地限制同时存在时，两者都必须满足；错误指出触发的是哪类限制。没有官方资料不等于无限制，也不能以 UI 能继续加插口为理由绕过执行前校验。
